# Configuration

The command line has a fixed form:

```text
cc_con <algorithm> --graph <graph.toml> --run <run.toml>
```

Graph specifications contain only input or generation settings. Run specifications
contain construction parameters and optional steps after construction. This allows the
same graph specification to be reused across BCC, BPA, CPA, DPF, FPA, LZF, and
later constructions.

The parser accepts a strict TOML subset: section headers, quoted strings,
integers, floating-point numbers, booleans, and `#` comments. Arrays, inline
tables, dates, and multiline strings are not accepted. Unknown or inapplicable
keys are errors. A relative path is resolved against the file that contains it.

Complete runnable files are under [`examples/`](../examples/README.md). There is
one graph specification for every accepted source and synthetic distribution,
and one statistics-only run specification for each construction. Any graph file
can be combined with any applicable construction run file through the fixed CLI.

The paper's graph specifications live in `config/graphs/`. For file-backed
graphs, place the source files under `datasets/suitesparse/` or
`datasets/cornell_arb/` at the repository root. Each specification gives the
exact subdirectory and filename. You can also point `datasets` to an existing
directory with this layout using a symlink. See the
[SuiteSparse example](../examples/README.md#run-on-a-suitesparse-graph).

## Graph specifications

`graph.name` is required because it determines report and cover filenames. It
must start with a letter or digit and contain only letters, digits, `.`, `-`, or
`_`.

Hypergraph clique projection:

```toml
[graph]
name = "groups-k8"
source = "synthetic"
model = "hypergraph"

[graph.parameters]
distribution = "k-uniform"
n = 100000
r = 250000
k = 8
seed = 19
```

The common parameters are integer `n >= 2`, integer `r >= 0`, and an optional
unsigned 32-bit `seed` that defaults to `19`. Select exactly one distribution and
its parameters:

| `distribution` | Additional parameters and restrictions |
| --- | --- |
| `k-uniform` | Integer `2 <= k <= n` |
| `poisson` | Finite `0 < lambda <= n` |
| `lognormal` | Finite `mu`, finite `sigma > 0`, and `mu <= log(n + 0.5)` |
| `power-law` | Finite `alpha > 0` and integers `2 <= s_min <= s_max <= n` |

Unknown keys and parameters belonging to another distribution are rejected
before generation. Poisson and lognormal sizes above `n` are resampled; their
compatibility restrictions keep that rejection practical. Sizes below two are
valid samples but contribute no edges. Isolate removal can make the
reported canonical `n` smaller than the requested value. Exact sampling,
deduplication, complexity, statistics, and reproducibility are described in
[`hypergraph-generation.md`](hypergraph-generation.md).

Matrix Market graph:

```toml
[graph]
name = "email-enron"
source = "file"
format = "mm"
path = "/absolute/path/email-Enron.mtx"
```

Coordinate matrices with pattern, integer, or real fields and general or
symmetric storage are accepted. Nonzero off-diagonal entries define edges.

Cornell/ARB real higher-order inputs use one of three explicit file formats:

```toml
# Parallel nverts/simplices files.
[graph]
name = "email-Enron"
source = "file"
format = "cornell-simplices"
nverts_path = "/absolute/path/email-Enron-nverts.txt"
simplices_path = "/absolute/path/email-Enron-simplices.txt"
```

```toml
# Incidence-dual projection: event vertices, one clique per original entity.
[graph]
name = "coPapers-DBLP"
source = "file"
format = "cornell-dual-simplices"
nverts_path = "/absolute/path/coauth-DBLP-full-nverts.txt"
simplices_path = "/absolute/path/coauth-DBLP-full-simplices.txt"
```

```toml
# One comma-separated hyperedge per line.
[graph]
name = "amazon-reviews"
source = "file"
format = "cornell-hyperedges"
path = "/absolute/path/hyperedges-amazon-reviews.txt"
```

Archive members, native statistics, and large-input considerations are
documented in
[`cornell-data.md`](cornell-data.md).

Extracted Stack Exchange tag-question assignment files have their own direct
coQuestions projection:

```toml
[graph]
name = "coQuestions-AskUbuntu"
source = "file"
format = "sx-tag-question"
path = "/absolute/path/parsed/askubuntu.txt"
```

Input semantics, projection statistics, and the distinction between source
question count and canonical `n` are documented in
[`stack-exchange-tag-questions.md`](stack-exchange-tag-questions.md).

Prepared CGF input normally uses the specification generated by `cg_prepare`:

```toml
# Generated file: email-enron.cgf.toml
[graph]
name = "email-enron"
source = "file"
format = "cgf"
path = "email-enron.cgf"
preparation_report = "email-enron.cgf.json"
preparation_report_sha256 = "<64 hexadecimal digits>"
```

The paths are relative to the generated TOML. For a normal construction run,
`cc_con` decodes every neighborhood after checking the header, offsets, record
boundaries, vertex IDs, and agreement with the preparation metadata. It does
not hash the CGF or sidecar, validate graph symmetry, or recompute the graph
fingerprint on every construction job. Run the explicit full check after
transfer or whenever corruption is a concern:

```text
cc_check graph --graph <graph.cgf.toml>
```

Generate all three files with:

```text
cg_prepare --graph <source.toml> --output-dir <directory>
```

## Run specifications

BPA, CPA, and FPA each have two construction parameters:

```toml
[construction]
tau = 4.0
label_selection = "min-label"
```

`tau` defaults to `4.0` and must be finite and at least `1`. The label rules are
`min-label`, `max-label`, `min-clique`, and `max-clique`.

BPA and FPA use direct two-pointer scans for `A[u] intersect A[v]`, and remove
individual labels with `lower_bound` followed by `vector::erase`. Although the
analysis charges intersection using a skew-aware
`O~(min{|A[u]|,|A[v]|})` implementation, the direct scan has been faster on
the evaluation graphs because it reads consecutive vector entries and often
finds a common label early. This direct scan has worst-case cost
`O(|A[u]|+|A[v]|)`, so it does not itself realize the skew-aware cost used in
the analysis. CPA uses the shared skew-aware intersection because Figure 4
requires it to retain the labels common to several tree edges.

BCC, DPF, and LZF have no construction parameters, so their run specifications
need only whichever common stages are desired:

```toml
[postprocess]
assignment_minimal = false

[verification]
enabled = false
```

The common `[postprocess]`, `[output]`, and `[verification]` sections can be used
with any algorithm. The `[construction]` section above applies only to BPA, CPA,
and FPA; using those keys with BCC, DPF, or LZF is rejected. The algorithm
remains a command-line argument, so the JSON report and filename identify which
construction consumed the run specification. See
[Assignment-Minimal Postprocessing](assignment-minimal.md) for the exact greedy
procedure and its cost.

## Optional CCF output

Every successful run produces a JSON statistics report. Cover output is
independent and optional:

```toml
[postprocess]
assignment_minimal = true

[output]
write_cover = true
directory = "/absolute/path/covers"

[verification]
enabled = false
```

CCF is the single persistent cover format, so there is no encoding choice. For
graph name `email-enron`, this writes `email-enron.ccf`; the directory must
exist. CCF output implies full semantic verification even when
`verification.enabled` is false. The JSON report records `cover-output` as the
verification trigger. CCF is written only after that check passes.

Omitting `[output]` produces statistics only. In that mode verification remains
optional and is controlled by `verification.enabled`.

There is no report setting in the run specification. Reports are always JSON and
are written to the process's current directory. A report name is reserved before
construction, so simultaneous repetitions in that directory receive distinct
numeric suffixes.
